# Worktrees

- When work needs worktrees, such as parallel variations, use Orca worktrees by default when working in an Orca context: the session runs in an Orca-managed terminal or sandbox, the current folder or worktree is managed by Orca, or I explicitly ask for Orca. Use the orca-cli skill to create and manage those worktrees; no separate request for Orca is needed in that context.
- Use session metadata (such as `ORCA_WORKTREE_ID`, `ORCA_TERMINAL_HANDLE`, `ORCA_PANE_KEY`, or `ORCA_TAB_ID`) or Orca's current-context lookup to identify an Orca context. An installed Orca executable or `ORCA_CLI_COMMAND` alone does not establish that context. Outside an Orca context, use your own tooling (the Agent tool's worktree isolation, or `git worktree add`). Follow any explicit request for a particular worktree tool.
- In an Orca context, delegating work to separate worktrees means launching Orca-managed worker agents in those worktrees, including requests for "subagents on worktrees" or an "agent team on worktrees". Creating Orca cards and pointing internal subagents at their folders does not satisfy this request. This applies to Claude and Codex, on the host and in the sandbox, and takes precedence over skill defaults that prefer internal subagents. Delegation that does not need separate worktrees may still use internal subagents unless I ask for Orca-managed agents.
- Use the orchestration skill when workers must report back, and the orca-cli skill for a handoff with nothing expected back. Load the session CLI's version-matched guide and its child-worktree placement reference before launching workers; let Orca create and launch their workspaces. Use the coordinating agent's harness (Claude or Codex) unless I specify another, and preserve any requested model.
- Verify that every worker has an Orca-managed agent session attached to its assigned card, so I can open the card and follow its work. Keep those sessions available after workers report back using Orca's keep-open option unless I request cleanup. If Orca cannot launch a worker, report the failure instead of silently substituting an internal subagent.
- Infer Orca worktree placement from the task. Parallel workers contributing to the current task belong under the current card: requests such as "implement this feature using 3 subagents on worktrees" or "use a Claude agent team on worktrees" mean create child Orca worktrees of the current task's card. Resolve that parent once before launching workers and use the same parent for every worker, rather than nesting workers under one another. Use `--parent-worktree active` from the coordinating workspace, or the exact resolved parent selector when creating elsewhere.
- A request such as "make a new worktree for this feature" or "make a worktree for this other thing" means create an independent top-level card in the same Orca project with `--no-parent`. If that new feature also needs parallel workers, create its top-level card first and place its workers under that card. Explicit requests for child, independent, or stacked work take precedence over these defaults.
- Keep both child and independent worktrees in the current project; creating a worktree does not authorize creating or registering a new project. For local same-project creation, omit `--repo` and `--project` so Orca resolves the project from the caller's directory. If context is ambiguous or a remote execution host requires a target, resolve the existing project and pass its exact selector; do not create a project to resolve ambiguity.
- Orca card placement and Git branch ancestry are separate. Independent cards use the project's default base unless I request a specific base or stacked work. For workers on the current feature, use the feature's branch as the base when they need its committed changes; a parent relationship alone does not select the Git base. Infer the placement from these rules without asking for routine confirmation; ask only when the intended project or parent cannot be resolved.
- When closing out or removing a worktree, check whether it is managed by Orca. If it is, use the Orca workflow to close out the corresponding Orca worktree as well.
- Scope cleanup to the worktree requested. If I explicitly identify a worktree, close out only that one; do not close other worktrees or sessions. Resolve “this worktree” to the current task's worktree, not every worktree in the repository.
