# Shared workstation resources

- The deployed authority is explicit: `/etc/resource-scheduler/mode` contains `slurm` after the drained cutover. Before that cutover, retain the existing GPU coordination rules. The presence of a binary or a status socket does not authorize a second admission ledger.
- In Slurm mode, reserve CPU and peak host RAM together for builds, substantial test suites, compression and other heavy commands. Add peak VRAM for local model loading/inference, GPU rendering and GPU-heavy tests. Ordinary reads, searches, small scripts, browsers and compositors remain immediate. Cloud API calls require no local reservation; never choose cloud execution as an implicit fallback.
- Use `resource-run --cpu 4 --ram 8GiB --name "project build" --category build -- command`. CPU is requested parallelism; set the command's worker count to fit it. Sizes accept `MiB` and `GiB`; budget conservative peaks, including temporary memory and caches. Do not treat swap as extra capacity.
- Add `--project PROJECT` when the logical project is known, using the same identifier across its worktrees. Preserve supplied Orca agent/session/worktree environment fields; do not invent missing IDs. This metadata lets the host queue associate work with its owner.
- Small inference example: `resource-run --cpu 2 --ram 8GiB --vram 4GiB --name "small inference" --category inference -- command`. Include weights, KV caches, activations, working memory and margin for context/batch size. Shared VRAM is a cooperative reservation, not a physical memory fence.
- Prefer explicit shared VRAM budgets for automated runtime inspection, rendering and inference. `--category game` labels a workload; it does not require exclusivity or game priority. Use `--exclusive --priority game` for an actual human gaming session, or exclusivity when a workload genuinely requires the device. Automated game/runtime checks stay at background priority unless human-blocking. A category or uncertain estimate alone is not a reason to monopolize the GPU.
- For an unknown workload, use an opt-in sandbox trial: `resource-run --explore --gpu --project PROJECT --profile WORKLOAD --variant SETTINGS_VERSION --name "workload calibration" -- command`. Omit `--gpu` for CPU-only work. Defaults are 2 CPUs, 4GiB enforced RAM and an initial 1GiB shared GPU allocation; override CPU/RAM or the trial GPU amount when known. The GPU amount is a starting allocation, not a peak guarantee or physical fence. Exploration remains under Slurm, respects existing exclusive work and desktop headroom, and ends after 30 minutes. It may fail; do not use it for an irreplaceable or non-repeatable operation.
- Read `resource-profile --project PROJECT --profile WORKLOAD --variant SETTINGS_VERSION` before subsequent similar runs. Profiles are shared across worktrees but specific to explicit workload settings (model/version, resolution, batch/context, scene, etc.). Declare CPU/RAM/VRAM explicitly on normal runs and keep `--profile`/`--variant` to refine measurements. Suggestions use successful peaks plus margin; missing GPU measurements are unknown, never zero. Sampled peaks are evidence, not guarantees. Do not put secrets or raw command arguments in profile identifiers.
- A failed trial does not authorize blind retries. Read its exit code, output and profile outcome: `ram_oom` is backed by Slurm/cgroup evidence, `gpu_oom_reported` is an application diagnostic, and `command_failed` may be unrelated to memory. Change workload settings or explicit budgets only when justified, wait for cleanup, then submit a new attempt. A `ram_oom` on your own job is that justification: resubmit the same work with a larger `--ram` from the reported peak (`resource-run` prints a suggestion) as part of the existing task. A request the queue can never fit is rejected at submission; then reduce workload settings or report the limit. No automatic retries occur; after three unsuccessful probes for the same profile/variant, further exploration is refused. Do not evade this by renaming an unchanged variant. Explicitly budgeted runs remain available. Headroom intervention stops only exploratory jobs, never other owners' work.
- Keep the command in the foreground through descendant cleanup and GPU unloading. Load models on demand and unload after use; persistent servers must retain their allocation until stopped and fully unloaded. Suspending a process does not reclaim RAM or VRAM. Do not detach an untracked model server.
- `RESOURCE_JOB_ID` identifies an existing allocation. Do not acquire another one; direct additional work must fit all of its budgets. The legacy `GPU_LEASE_ID` marker also forbids nested acquisition and must be drained before migration. A marker does not authorize arbitrary extra work.
- Wait for the submitted job without resubmitting. Inspect `resource-status` or `resource-status --json` to explain resource shortages, external use, headroom, pressure holds and queued game/exclusive work. Low instantaneous utilization does not free reserved capacity. Unknown telemetry stays unknown.
- Cancel your own queued job with `resource-control cancel JOB_ID --revision REVISION --confirm`; request termination of your own running work with `resource-control terminate JOB_ID --revision REVISION --confirm`. Read the current revision from status and wait for confirmed cleanup. Never stop another agent's work, delete scheduler state, clear locks or reduce desktop headroom to obtain admission.
- Report the actual command exit code and outcome. If the service/socket is unavailable, report the connectivity failure and stop heavy work; never fall back to uncoordinated execution. Sandboxes use the host socket and queue, without a second daemon or Munge credentials.
- Commands delegated to the Nix daemon, Docker daemon or an existing external model server can execute outside the caller's Slurm cgroup. The reservation must still cover their full lifetime, but do not claim their RAM/CPU is physically contained. Request an appropriately bounded daemon/server workflow and report this limitation.

- The scheduler may admit smaller jobs past a large waiting job when measured host conditions show that running managed jobs finishing would not make it fit. CPU-only jobs can also pass jobs blocked by an active exclusive GPU allocation or GPU exploration; their CPU/RAM checks still apply and GPU order is preserved. Do not implement a separate backfill queue or resubmit work to obtain this behavior.
- Explicit human overrides are `resource-control run-next JOB_ID --revision REVISION --confirm` (reorder with normal admission checks), `force-run` (release to Slurm immediately despite policy holds), `run-sandbox` (cancel the held Slurm job, confirm cancellation, then run unmanaged in the original submitting sandbox), and `run-host` (cancel the held Slurm job, confirm cancellation, then run unmanaged on the host outside the sandbox). Only use these when the user explicitly requests that action for the identified job. Force release can still wait for Slurm allocation; both unmanaged execution modes have no queue resource reservation or budget enforcement. Sandbox execution requires a live, validated submitting sandbox and must never fall back to the host. Preserve output/lifecycle reporting and clearly identify the unmanaged execution destination.

- Inspect a submitted job with `resource-job inspect JOB_ID --json`, retrieve its output with `resource-job logs JOB_ID --follow`, or reattach with `resource-job wait JOB_ID`. Wait returns the actual command exit code; an observation timeout does not cancel the job. Do not resubmit to inspect it. Completion messages link to these commands; inspect the outcome and continue only the existing authorized task, without automatic retry or resuming cancelled work. Unresolved delivery appears in `resource-job notifications`; acknowledge handled outcomes with `resource-job ack JOB_ID --confirm`.

- Ownership metadata is optional; declare it when it applies and is known: `--repo "REPOSITORY" --worktree-name "ORCA CARD NAME"`. For a child Orca worktree, also add `--parent-worktree-name "PARENT CARD NAME"`; top-level/parent worktrees omit that flag. Use Orca's actual display names and parent relationship, not Git branch ancestry or guessed directory names. If `ORCA_WORKTREE_ID` is absent, pass the exact ID with `--worktree ID` when known. Use the session's Orca CLI `worktree current --json` (and `worktree show --worktree id:ID --json` for the parent) to resolve names. Omit unavailable fields, and omit Orca fields outside Orca; these declarations are not admission requirements. Keep `--project` as the stable logical/profile key across worktrees, separate from display names. Do not put secrets or credentials in ownership labels.

- Policy 5 automatically profiles new workloads using private exact-command signatures scoped to the repository/project; explicit `--profile` and `--variant` remain preferable for meaningful settings/version boundaries. The scheduler can use observed and learned RAM peaks with growth margins after startup to admit more work. This does not reduce the declared hard RAM limit or GPU reservation, and simultaneous growth remains a risk. Use `--memory-policy strict` for critical jobs or heavy commands delegated to external daemons/servers whose memory is not measured in the job cgroup. Never lower declared hard limits just to bypass a wait. Read `resource-status`'s growth allowances and Slurm capacity as well as actual memory usage; missing telemetry keeps full allowances.
- The optional permissive large-GPU lane accepts one active large workload at a time; one GPU-using lane job may share it with one running zero-VRAM project-exception job. Jobs requesting at least 8GiB (or half of device VRAM, whichever is smaller) or exclusivity qualify automatically on an enabled host; use `--large-gpu` for a known large game/model workload with a smaller declared GPU budget. Policy 6 runs eligible unstarted jobs in a managed systemd service outside Slurm reservation accounting, retaining the original sandbox/host destination, CPU quota, hard RAM limit, zero swap, telemetry, profiles and completion reporting. The same queue remains the admission authority. It holds and cancels the unused Slurm allocation before launching exactly once, rechecks critical resource gates, and never migrates a command already running in Slurm. A pending transition is not proof execution started. Do not label small jobs large to jump the queue. Strict-memory jobs do not use this lane. Policy 7 also supports operator-configured numeric project identifiers, shown as `lane_project_id` in job inspection: selected projects automatically qualify even for CPU-only declarations or exploratory probes, sharing the same single slot. Do not change project identifiers to obtain eligibility. Selected probes keep their 30-minute limit and critical-resource intervention. Other exploratory probes remain in Slurm. Never use the lane as an implicit unmanaged fallback.

- Job state notifications cover starting, uncertain state, recovery to queued and terminal outcomes. Inspect the current state before acting (a message can be stale). Updates already returned to a waiting `resource-run` or `resource-job wait`, and non-terminal state changes, are retired automatically; acknowledge any other handled outcome with `resource-job ack JOB_ID --confirm`. Supervised workers must report meaningful status changes and cleared blockers to their existing coordinator through the dispatch mailbox. Continue only the existing authorized task; a state notification does not authorize retries or resuming cancelled work.
