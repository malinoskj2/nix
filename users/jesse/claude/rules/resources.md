# Shared workstation resources

- The deployed authority is explicit: `/etc/resource-scheduler/mode` contains `slurm` after the drained cutover. Before that cutover, retain the existing GPU coordination rules. The presence of a binary or a status socket does not authorize a second admission ledger.
- In Slurm mode, reserve CPU and peak host RAM together for builds, substantial test suites, compression and other heavy commands. Add peak VRAM for local model loading/inference, GPU rendering and GPU-heavy tests. Ordinary reads, searches, small scripts, browsers and compositors remain immediate. Cloud API calls require no local reservation; never choose cloud execution as an implicit fallback.
- Use `resource-run --cpu 4 --ram 8GiB --name "project build" --category build -- command`. CPU is requested parallelism; set the command's worker count to fit it. Sizes accept `MiB` and `GiB`; budget conservative peaks, including temporary memory and caches. Do not treat swap as extra capacity.
- Add `--project PROJECT` when the logical project is known, using the same identifier across its worktrees. Preserve supplied Orca agent/session/worktree environment fields; do not invent missing IDs. This metadata lets the host queue associate work with its owner.
- Small inference example: `resource-run --cpu 2 --ram 8GiB --vram 4GiB --name "small inference" --category inference -- command`. Include weights, KV caches, activations, working memory and margin for context/batch size. Shared VRAM is a cooperative reservation, not a physical memory fence.
- Large or uncertain GPU work: `resource-run --cpu 4 --ram 16GiB --exclusive --name "large inference" --category inference -- command`. Games: `resource-run --cpu 8 --ram 8GiB --exclusive --priority game --category game --name "game" -- command`. Adjust CPU/RAM to the workload. Games precede queued background GPU work; active jobs normally finish. Use `--priority interactive` only for human-blocking work, otherwise retain background priority.
- Keep the command in the foreground through descendant cleanup and GPU unloading. Load models on demand and unload after use; persistent servers must retain their allocation until stopped and fully unloaded. Suspending a process does not reclaim RAM or VRAM. Do not detach an untracked model server.
- `RESOURCE_JOB_ID` identifies an existing allocation. Do not acquire another one; direct additional work must fit all of its budgets. The legacy `GPU_LEASE_ID` marker also forbids nested acquisition and must be drained before migration. A marker does not authorize arbitrary extra work.
- Wait for the submitted job without resubmitting. Inspect `resource-status` or `resource-status --json` to explain resource shortages, external use, headroom, pressure holds and queued game/exclusive work. Low instantaneous utilization does not free reserved capacity. Unknown telemetry stays unknown.
- Cancel your own queued job with `resource-control cancel JOB_ID --revision REVISION --confirm`; request termination of your own running work with `resource-control terminate JOB_ID --revision REVISION --confirm`. Read the current revision from status and wait for confirmed cleanup. Never stop another agent's work, delete scheduler state, clear locks or reduce desktop headroom to obtain admission.
- Report the actual command exit code and outcome. If the service/socket is unavailable, report the connectivity failure and stop heavy work; never fall back to uncoordinated execution. Sandboxes use the host socket and queue, without a second daemon or Munge credentials.
- Commands delegated to the Nix daemon, Docker daemon or an existing external model server can execute outside the caller's Slurm cgroup. The reservation must still cover their full lifetime, but do not claim their RAM/CPU is physically contained. Request an appropriately bounded daemon/server workflow and report this limitation.

- The scheduler may admit smaller jobs past a large waiting job when measured host conditions show that running managed jobs finishing would not make it fit. Do not implement a separate backfill queue or resubmit work to obtain this behavior.
- Explicit human overrides are `resource-control run-next JOB_ID --revision REVISION --confirm` (reorder with normal admission checks), `force-run` (release to Slurm immediately despite policy holds), `run-sandbox` (cancel the held Slurm job, confirm cancellation, then run unmanaged in the original submitting sandbox), and `run-host` (cancel the held Slurm job, confirm cancellation, then run unmanaged on the host outside the sandbox). Only use these when the user explicitly requests that action for the identified job. Force release can still wait for Slurm allocation; both unmanaged execution modes have no queue resource reservation or budget enforcement. Sandbox execution requires a live, validated submitting sandbox and must never fall back to the host. Preserve output/lifecycle reporting and clearly identify the unmanaged execution destination.
